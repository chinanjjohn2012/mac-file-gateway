# Multi-Workspace Phase 2 Controlled Exec Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add explicitly authorized per-Workspace Controlled Exec to Multi mode, without weakening existing Phase 1 file APIs or Legacy exec/Local Skills.

**Architecture:** Reuse the existing `CommandRunner` and add a single-owner `ExecSupervisor` that controls spawn, native process-group identity, cancellation, drain and lifetime leases. `WorkspaceService` alone authorizes Workspace execution; HTTP/MCP only adapt strict arguments. No OS sandbox is claimed.

Starlette, MCP SDK, Uvicorn, AnyIO, pytest, Python `subprocess`, native macOS process signals, Pipenv and Go.

## Pre-implementation contracts resolving IP1–IP3

**IP1: spawn attempts rather than assumed execution.** A unique admitted ticket may make **zero or one** actual `Popen` call. Denied/dry-run/pre-spawn-cancelled: `Popen_attempts=0, marker=0`. Once the apply branch is authorized and enters the actual spawn attempt: `Popen_attempts=1` even when Popen raises; marker stays 0 if it never started. On successful launch followed by response loss/re-entry: ≤1 attempt and ≤1 synthetic marker for that one ticket. An independent later request has a **different ticket** and may execute again. Counting only markers is insufficient; no assertion may require one spawn from every admitted request.

**IP2 / LC1: actual cwd qualification is a two-legged gate: a usable successful launch **AND** race safety.** Task 3 adds `gateway/executor.py` and a `VerifiedCwdLease` (or equivalently named context-managed structure) containing a pinned no-follow actual-cwd FD, expected `st_dev/st_ino`, and the root/workspace lease. A bare `Popen(cwd=str(path))`, a re-stat just before Popen, or merely holding the FD does not atomically bind child cwd to the authorized object.

**Disqualified prior candidate (LC1 evidence):** `Popen(cwd=f"/dev/fd/{cwd_fd}", pass_fds=(cwd_fd,), shell=False, start_new_session=True)` was tested in a synthetic macOS arm64/Python 3.14.7 environment: both *unchanged* cwd and *renamed/recreated* cwd returned `NotADirectoryError/ENOTDIR`; the target never ran. An ordinary string-path positive completed, but **does not qualify this FD candidate**. The current FD-path candidate must be marked **QUALIFICATION FAIL / STOP**; no production `gateway/executor.py` change may enable it on that evidence. This is a scoped native result, not an assertion about all Darwin versions.

**Qualification protocol for a separately designed/approved alternative:** before Task 3 native handoff can pass, **the same launch mechanism** must complete a *non-racing* real synthetic child successfully (`exit_code=0`, marker present, child `cwd st_dev/st_ino` equals authorized actual-cwd FD); cover **direct and pipenv**, ordinary sibling directories, selected runner, **automatic and explicit Pipfile** scope binding. These *normal positive controls are mandatory* and **cannot** pass via safe error. Only after these positives succeed can rename/recreate selected cwd or ancestors at a barrier before spawn be counted as race negatives; in those negatives, the child must either use the original verified object or fail **before any target marker**. A fake launcher that always raises must make `qualified=false` even if all race negatives safely fail. Prove cancellation/error FD and permit cleanup. The 1-Popen-at-most rule and process-group identity must survive the design.

No alternative is currently approved. Investigate candidates only in isolated test-only native probes, then record OS/Python support, interface, once-only spawn semantics and an independent architecture review/**owner decision** before committing production launch coupling. A `posix_spawn` fchdir file action is only a research direction, **not** an approved fallback; if it replaces Popen or changes the approved attempt accounting/Legacy contract, obtain explicit design/owner approval. **Never** silently substitute path strings, process-global `chdir`, multithreaded `preexec_fn` or an uncounted helper process.

**IP3 / PR2: MCP cancellation has a unique session-scoped wire request identity.** For a Multi Gateway with **any** exec-enabled Workspace, choose MCP SDK `stateless_http=False` on the existing `/mcp` endpoint and retain `json_response=True` if verified with the pinned SDK; require `initialize` and server-validated `Mcp-Session-Id` on subsequent POSTs. Pure file-only Multi (`exec.enabled=false` everywhere) retains Phase 1 `stateless_http=True`; Legacy remains unchanged. Existing file tools must continue working through the same **stateful** session when Multi exec is enabled. If required clients cannot negotiate it, stop and request design/owner review.

**PR2/PR3 protocol admission must precede the FIRST SDK ID-indexed transport state mutation, as well as in-flight responder registration.** The MCP base protocol requires a requestor not to reuse a wire request ID **during the entire same session**, even after the earlier request finished; a `notifications/cancelled` message carries requestId but **no server ticket/generation**. SDK 1.30.0 can accept an invalid repeated ID and then route a late cancel to its new responder. Therefore an **authenticated, session-owned, atomic seen-request-ID guard** must run on incoming client-to-server JSON-RPC *requests*, after verifying the SDK session identity but **before the first `_request_streams`/other ID-indexed transport write**, `_in_flight` registration, any business dispatch, or a `Popen` attempt. Rejecting an invalid duplicate must leave the original HTTP response channel and responder untouched. Reject concurrent or completed repeats (`dispatch=0, Popen_attempts=0`), without replacing/cancelling the original responder; return a bounded protocol/transport error, not a fake tool execution result. Preserve the JSON-RPC ID value/type under its specified ID rules; **integer `71` and string `"71"` are different valid IDs and must not alias**. Do not interpret a legal mixed-type pair as a duplicate just because a transport uses `str(id)`. Never use bare requestId across sessions. The guard is not an application-level idempotency cache.

**PR3/P2 transport-routing qualification, independent of the PR2 duplicate guard.** In the pinned MCP SDK 1.30.0, `streamable_http.py` writes `_request_streams[str(message.root.id)]` **before** `BaseSession._in_flight`; the response router similarly indexes by `str(response.id)`, and `GET_STREAM_KEY="_GET_stream"` lives in the same transport map. An isolated SDK ASGI experiment reproduced that simultaneous legal request IDs integer `71` and string `"71"` can misroute A's typed result to B and strand A. At the `b82a475` review, the `"_GET_stream"`/GET hazard was source-derived only. The later fixed PR3 report linked above records isolated GET/cancel/cleanup reproductions and candidate results; these are not real Gateway or target-client acceptance. Preserve the earlier report's evidence boundary rather than rewriting it.

**Transport contract:** for every accepted session, use an authenticated session namespace and a **collision-free, lossless internal route identity** across first request-stream registration, response and related-message routing, cancellation, output/stream cleanup and session termination. Route identity must distinguish protocol ID **type and value**, and use a **disjoint internal namespace for GET/transport sentinels**. External request/response/cancellation IDs must retain their legal JSON-RPC values and types. Duplicate-ID rejection must occur atomically before any ID-indexed SDK state mutation and must neither replace nor close the original channel/responder/ticket. Internal route keys may use tagged identity tuples or an equally demonstrated equivalent, but no lossy `str(id)` aliasing, legal-ID rejection, silent protocol narrowing, or SDK monkey-patch without independent review is approved.

**Qualification gate (must be demonstrated using the selected SDK/adapter, not a fake key map):** two real concurrent POSTs with integer `71` and string `"71"` each complete with the **original typed response.id and corresponding distinct result**; numeric-numeric and string-string positive pairs still succeed. A real GET/SSE channel and a concurrent POST with legal string ID `"_GET_stream"` coexist without overwrite, mistaken cleanup or cancellation (isolated research is recorded; real Gateway/client qualification is still required). Concurrent and completed same-type ID duplicates are rejected **before** the first `_request_streams` or any equivalent ID-keyed write (`transport_registration=0` for the duplicate, `dispatch=0`, `Popen_attempts=0`), while the original request's HTTP stream and responder finish normally. Same-session targeted cancel, cross-session identical IDs, typed-ID related messages, request completion/close and session-cap exhaustion must not misroute or clean another owner's state. Assertions must observe routing identity *and* correct successful deliveries—rejecting all requests fails the gate. Run the isolated SDK ingress proof **before** freezing Task 3/4 MCP ticket interface; later repeat on the real Gateway listener and required clients.

**STOP:** SDK 1.30.0 is **not qualified** by its unmodified routing behaviour under this test. If a safe ingress hook before the first write **and collision-free full route mapping** cannot be demonstrated, **STOP the MCP/exec transport integration and Task 3/4 MCP identity handoff**, and seek architecture/owner review for an SDK upgrade, vetted adapter or other mechanism. None is currently selected or authorized; do not silently change ID semantics, add a public cancel/job API, or treat an HTTP 202/SDK mock as proof. This does **not** stop Task 1 native test-only PGID research, Task 2 Legacy security repairs, or Task 3's isolated static work.

**Session/seen-ID lifecycle:** retain all previously used IDs for the whole valid session lifetime. Do not evict used IDs while the session can still accept messages: cap memory with an explicit per-session request count/TTL tied to the SDK session lifetime, and on exhaustion reject further requests or safely terminate that session and require `initialize` for a **new** session. Do not silently evict and then permit an old ID. On session termination, retire the session, tickets and guard atomically; delayed events from the old session must not target a new one. If no verified extension seam exists **before the first transport ID-indexed write**, or the SDK's routing/cleanup cannot satisfy PR3's complete valid-ID domain, **STOP Task 5 and Task 3/4 MCP ticket-binding finalization**. Do not count a pre-responder-only guard as qualified.

**Transport cancellation and internal tickets are different layers.** A client cancel notification from a separate POST in **the same validated session** may cancel only that session's still-active original request. Map (`session identity`, **lossless typed wire requestId and transport route identity**) to a server-created ticket/generation **before** submitting the sync worker. A late wire cancel for **completed A/ID71** is ignored; a later valid B in that session uses **new ID72** and cannot be affected. Different sessions may each use ID71, and cancellation in one never affects the other. A repeated ID71 in the same session is invalid and must never reach the SDK responder or worker. Generation only prevents **internal** stale timers/callbacks/compare-and-remove from affecting successors; it **cannot** disambiguate a wire cancel lacking generation if the illegal ID reuse were admitted.

Before worker dispatch, register ticket mapping and latch early cancellation; notify `ExecSupervisor.cancel(ticket_id, reason)` and **shield actual worker cleanup** so AnyIO waiter cancellation cannot abandon the process. Remove active mapping via identity-safe compare-and-remove only after real worker completion; retain the session's **seen-ID tombstone** separately until session expiration. An independent retry must use a new ID in the same session, or a new session where the old number is permitted; either produces a new ticket and may run again—there is **no cross-request dedup**. REST disconnect is independent and, when unobservable, bounded by command timeout. HTTP `202` alone does not prove cancellation. This is standard MCP cancellation, not a new public cancel/job API.
