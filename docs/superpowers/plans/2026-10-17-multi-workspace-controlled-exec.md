# Multi-Workspace Phase 2 Controlled Exec Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add explicitly authorized per-Workspace Controlled Exec to Multi mode, without weakening existing Phase 1 file APIs or Legacy exec/Local Skills.

**Architecture:** Reuse the existing `CommandRunner` and add a single-owner `ExecSupervisor` that controls spawn, native process-group identity, cancellation, drain and lifetime leases. `WorkspaceService` alone authorizes Workspace execution; HTTP/MCP only adapt strict arguments. No OS sandbox is claimed.

**Tech Stack:** Python 3.11+ for Legacy/file-only; **macOS Python 3.13+ for Phase 2 Multi exec**, subject to a native `WNOWAIT`/PGID qualification gate. Starlette, MCP SDK, Uvicorn, AnyIO, pytest, Python `subprocess`, native macOS process signals, Pipenv and Go.

**Spec:** `docs/superpowers/specs/2026-10-17-multi-workspace-controlled-exec-design.md` at the approved conditional-freeze design base `a7a3f87772ad13545facff48620db68f12ac8ef3`. Third independent design review: **CONDITIONAL**, zero new P findings; not functional PASS.

## Global Constraints

- **Approved 2026-10-17 product values:** extend `schema_version:1`; `paths:["."]` requires explicit administrator authorization; 1 active exec per Workspace and 4 global; TERM grace 2 seconds, separate drain budget 2 seconds; no public remote cancel API; **at most one `Popen` attempt per admitted request** (`Popen_attempts <= 1`; rejected/dry-run/pre-spawn-cancelled requests have 0), **no dedup between independent requests**.
- **Python version boundary:** existing Legacy and file-only functionality continues to support Python 3.11+. Phase 2 Multi exec on macOS requires Python **3.13+**. This is a capability gate, **not** permission to raise the whole Gateway's minimum version or to execute unsafe fallback `killpg` on unsupported versions. Validate version before listener/exec activation. Document any non-macOS platform support explicitly; do not claim `WNOWAIT` is safe on a platform before native evidence.
- **Review gating:** API and security invariants are conditionally frozen. Exact `WNOWAIT`/unreaped-leader mechanism is *not* qualified. If Task 1 native proof fails, **STOP Task 4 and dependent Multi exec integration/release**, return the OS anchor mechanism to design review; **Task 2 and Task 3 pure parsing/admission work remain independently allowed** when separately authorized. **LC1: the previously selected `/dev/fd/<fd>` cwd launch candidate is empirically NOT QUALIFIED on the tested macOS arm64/Python 3.14.7 environment (`ENOTDIR` even without rename). No working actual-cwd launcher is currently approved; Task 3 native execution handoff and Task 4 MUST STOP pending new reviewed mechanism and native positive proof.** **PR2: no repeated MCP request ID may be dispatched within one stateful session; enforce before SDK responder registration.** No unchecked numeric PGID signalling.
- **Pre-existing safety defects:** D1/P1 Go hook alias and D2/P2 option-path bypass in shared Legacy `CommandRunner` must be fixed, with pytest R1 indirect argv rejection, *before* Multi exec routes are made runnable.
- Multi mode remains disabled by default. Skills are Phase 3 and stay disabled; Legacy single-root API and behaviour must remain compatible except explicitly prohibited dangerous argv.
- No production policy, real credentials, real project scripts, Tunnel, or running Gateway changes; use synthetic roots and processes only.
- Work on a separate feature branch/worktree; one testable task and security review per change. Never merge or deploy without subsequent explicit authorization.
- On Mac, verify SIGINT and SIGTERM with a live synthetic Gateway listener. Existing CI/Manifest success is not Phase 2 functionality proof.

## Review Focus

The five easy-to-miss scenarios are each owned by the tasks below: (1) pytest short-option clusters, `--`, and `@` indirection (Task 2); (2) native actual-cwd dev/ino changing between validation and spawn, including Pipfile binding (Tasks 3/4); (3) leader exit with original-group descendants still alive or holding pipes (Tasks 1/4); (4) SDK cancellation sent by a second POST or a cancelled worker queued before spawn (Tasks 3/5); (5) lost response and independent retry after side effects (Tasks 4/6).

## Pre-implementation contracts resolving IP1–IP3

**IP1: spawn attempts rather than assumed execution.** A unique admitted ticket may make **zero or one** actual `Popen` call. Denied/dry-run/pre-spawn-cancelled: `Popen_attempts=0, marker=0`. Once the apply branch is authorized and enters the actual spawn attempt: `Popen_attempts=1` even when Popen raises; marker stays 0 if it never started. On successful launch followed by response loss/re-entry: ≤1 attempt and ≤1 synthetic marker for that one ticket. An independent later request has a **different ticket** and may execute again. Counting only markers is insufficient; no assertion may require one spawn from every admitted request.

**IP2 / LC1: actual cwd qualification is a two-legged gate: a usable successful launch **AND** race safety.** Task 3 adds `gateway/executor.py` and a `VerifiedCwdLease` (or equivalently named context-managed structure) containing a pinned no-follow actual-cwd FD, expected `st_dev/st_ino`, and the root/workspace lease. A bare `Popen(cwd=str(path))`, a re-stat just before Popen, or merely holding the FD does not atomically bind child cwd to the authorized object.

**Disqualified prior candidate (LC1 evidence):** `Popen(cwd=f"/dev/fd/{cwd_fd}", pass_fds=(cwd_fd,), shell=False, start_new_session=True)` was tested in a synthetic macOS arm64/Python 3.14.7 environment: both *unchanged* cwd and *renamed/recreated* cwd returned `NotADirectoryError/ENOTDIR`; the target never ran. An ordinary string-path positive completed, but **does not qualify this FD candidate**. The current FD-path candidate must be marked **QUALIFICATION FAIL / STOP**; no production `gateway/executor.py` change may enable it on that evidence. This is a scoped native result, not an assertion about all Darwin versions.

**Qualification protocol for a separately designed/approved alternative:** before Task 3 native handoff can pass, **the same launch mechanism** must complete a *non-racing* real synthetic child successfully (`exit_code=0`, marker present, child `cwd st_dev/st_ino` equals authorized actual-cwd FD); cover **direct and pipenv**, ordinary sibling directories, selected runner, **automatic and explicit Pipfile** scope binding. These *normal positive controls are mandatory* and **cannot** pass via safe error. Only after these positives succeed can rename/recreate selected cwd or ancestors at a barrier before spawn be counted as race negatives; in those negatives, the child must either use the original verified object or fail **before any target marker**. A fake launcher that always raises must make `qualified=false` even if all race negatives safely fail. Prove cancellation/error FD and permit cleanup. The 1-Popen-at-most rule and process-group identity must survive the design.

No alternative is currently approved. Investigate candidates only in isolated test-only native probes, then record OS/Python support, interface, once-only spawn semantics and an independent architecture review/**owner decision** before committing production launch coupling. A `posix_spawn` fchdir file action is only a research direction, **not** an approved fallback; if it replaces Popen or changes the approved attempt accounting/Legacy contract, obtain explicit design/owner approval. **Never** silently substitute path strings, process-global `chdir`, multithreaded `preexec_fn` or an uncounted helper process.

**IP3 / PR2: MCP cancellation has a unique session-scoped wire request identity.** For a Multi Gateway with **any** exec-enabled Workspace, choose MCP SDK `stateless_http=False` on the existing `/mcp` endpoint and retain `json_response=True` if verified with the pinned SDK; require `initialize` and server-validated `Mcp-Session-Id` on subsequent POSTs. Pure file-only Multi (`exec.enabled=false` everywhere) retains Phase 1 `stateless_http=True`; Legacy remains unchanged. Existing file tools must continue working through the same **stateful** session when Multi exec is enabled. If required clients cannot negotiate it, stop and request design/owner review.

**Protocol admission must precede SDK in-flight responder registration.** The MCP base protocol requires a requestor not to reuse a wire request ID **during the entire same session**, even after the earlier request finished; a `notifications/cancelled` message carries requestId but **no server ticket/generation**. SDK 1.30.0 can accept an invalid repeated ID and then route a late cancel to its new responder. Therefore use an **authenticated, session-owned, atomic seen-request-ID guard** on incoming client-to-server JSON-RPC *requests*, after validating the SDK's session identity but **before** SDK `_in_flight` registration, any business dispatch, or a `Popen` attempt. Reject concurrent or completed repeats (`dispatch=0, Popen_attempts=0`), without replacing/cancelling the original responder; return a bounded protocol/transport error, not a fake tool execution result. Preserve JSON-RPC ID value/type under its specified ID rules; never use bare requestId across sessions. The guard is not an application-level idempotency cache.

**Session/seen-ID lifecycle:** retain all previously used IDs for the whole valid session lifetime. Do not evict used IDs while the session can still accept messages: cap memory with an explicit per-session request count/TTL tied to the SDK session lifetime, and on exhaustion reject further requests or safely terminate that session and require `initialize` for a **new** session. Do not silently evict and then permit an old ID. On session termination, retire the session, tickets and guard atomically; delayed events from the old session must not target a new one. If there is no verified extension seam **before SDK responder registration**, STOP Task 5 and the Task 3/4 ticket-binding finalization for review instead of promising a guarantee an adapter cannot enforce.

**Transport cancellation and internal tickets are different layers.** A client cancel notification from a separate POST in **the same validated session** may cancel only that session's still-active original request. Map (`session identity`, unique `wire requestId`) to a server-created ticket/generation **before** submitting the sync worker. A late wire cancel for **completed A/ID71** is ignored; a later valid B in that session uses **new ID72** and cannot be affected. Different sessions may each use ID71, and cancellation in one never affects the other. A repeated ID71 in the same session is invalid and must never reach the SDK responder or worker. Generation only prevents **internal** stale timers/callbacks/compare-and-remove from affecting successors; it **cannot** disambiguate a wire cancel lacking generation if the illegal ID reuse were admitted.

Before worker dispatch, register ticket mapping and latch early cancellation; notify `ExecSupervisor.cancel(ticket_id, reason)` and **shield actual worker cleanup** so AnyIO waiter cancellation cannot abandon the process. Remove active mapping via identity-safe compare-and-remove only after real worker completion; retain the session's **seen-ID tombstone** separately until session expiration. An independent retry must use a new ID in the same session, or a new session where the old number is permitted; either produces a new ticket and may run again—there is **no cross-request dedup**. REST disconnect is independent and, when unobservable, bounded by command timeout. HTTP `202` alone does not prove cancellation. This is standard MCP cancellation, not a new public cancel/job API.
