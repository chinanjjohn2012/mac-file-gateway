# 独立代码复审规则 V2.0 — 通用规则

`RULESET_ID: ICR-V2.0`  
**适用**：三角色工作流（A Developer，B Standards，C Spec）在明确受审对象和安全授权下的代码复审，不假定 GitHub、特定数据库/SDK/语言/运行平台。
**安全原则**：本规则只有在获得明确批准、完成三个 Project 的同版全文读取核验并指定生效轮次后，才能成为当前权威规范。不得通过文件改名自动批准证据替代、RED→GREEN 调整或生产安全门禁变更。

## 一、定义和身份

- **REVIEW_TARGET**：PR/变更集/模块/阶段，明确被验收的代码及制品集合；不可笼统写“整个项目已通过”。
- **CONTRACT_SCOPE**：适用的权威设计、行为与安全合同及版本；`FULL` 表示对该明确范围的完整审查。
- **SNAPSHOT_ID**：受审对象的可重建身份，须绑定内容、依赖/运行输入及必要有效差异；无版本的聊天粘贴和未验证本地文件不能冒充可复核快照。
- **REVIEW_ROUND**：审查轮次，旧轮次不会因为新规则、修改 Base、提交、重构或合并而自动迁移结论。
- **REVIEWER_INDEPENDENCE**：独立取证、独立提出反例及判断；在相同账户下的 B/C 会话不等于两个不同 GitHub 身份或两个自然人。
- **EVIDENCE_PROFILE**：与受审范围及测试要求匹配的验证方法，具体实现在适配文件定义；缺失关键证据必须拒绝超范围 PASS。

## 二、R01–R10 通用审查合同

### R01 — 快照身份、完整性与稳定性

1. 每轮声明 `REVIEW_TARGET / CONTRACT_SCOPE / SNAPSHOT_ID`，直接核验其代码集合、有效差异、权威规则与合同版本。
2. 记录审查对象之外但会影响执行的依赖、配置、生成源或制品；不能从有限可见源推断整个实际执行环境。
3. 开始和结束独立核验快照一致性，发现实质漂移必须评估影响、停止旧快照无条件 PASS 并重新绑定所需验证。
4. 完整性证据必须覆盖**文件集合与内容**；哈希、Tree、Manifest、制品证明只是按适用证据规范选择的实现工具。
5. 无法确定代码版本、输入身份或完整性的部分不得被宣称为审查通过；本地未提交、远端已提交和混合源须明确区分。

### R02 — 两条独立审查与身份真实表述

1. B 独立 Standards、C 独立 Spec，分别读取权威合同/源码/原始证据、提出反例、记录结果；不得引用另一评审者的 PASS 代替自己判断。
2. 开发者 A 的自检、汇总和协调不能代替任何独立审查签收；两份报告必须绑定同一适用的受审快照及轮次。
3. 独立性按`会话/取证/账户/人员`四维明确声明；项目要求独立人类或不同组织审查时须另行满足，不得以 ChatGPT 会话替代。
4. 两份当前有效角色 Review 均满足足够范围是整体放行的必要条件，不是充分条件。

### R03 — 以完整合同建立覆盖矩阵

1. 从当前权威设计/规范和代码调用链建立目标范围的覆盖矩阵，不只检查本次差异。
2. 检查新行为、既有合法路径、安全/限制、不同执行模式、异常/取消/超时/重试/恢复、并发和状态变化等**实际适用项**。
3. 对不适用项给出可检验理由，对证据不足项明确记录缺口；不得直接删除难测的合同。
4. `FULL` 必须明确范围边界，不可由一个修复点的覆盖推断整个系统。

### R04 — 合法成功、非法拒绝、边界与异常

1. 对每项重要适用合同检查成功行为与禁止行为两面，并考虑边界与异常情形。
2. 若合同不具有某类输入或拒绝语义，应记录不适用依据；不能机械制造无意义测试，也不能以 N/A 绕过安全合同。
3. 必须区分实际执行、独立静态推论、Mock/替身及未执行，不得虚构覆盖。

### R05 — 真实相邻影响与回归风险

1. 按依赖图、调用链、共享状态/资源、执行模式、平台适用性评估未修改路径。
2. 关注原有合法能力与安全限制是否受损；对有风险的相邻路径执行必要回归或明确阻断证据缺口。
3. 不要求所有项目测试不适用的数据库、接口、架构和部署形态；项目专属示例属于专项清单，不写进核心强制规则。

### R06 — 独立主动反例

1. B/C 不得仅重跑开发者提供的成功测试，每个高风险变更点至少独立设计一个有意义的反例。
2. 优先针对遗漏的入口、状态、并发、失败恢复与权限边界；确实无法安全执行时记录原因及审查结论影响。
3. 独立的静态反例不应冒充实际执行通过，Mock 不应冒充真实调用链。

### R07 — 可追溯的执行与证据链

1. 建立受审对象、执行的实际代码和环境、测试动作、输出日志及退出状态之间的身份联系。
2. 只有被测执行环境和合同所需路径有直接证据时才声明对应执行验证；开发者摘要、单元测试 GREEN 和平台状态徽章均不能替代原始证据。
3. 真实组件/集成/环境与 Mock、离线探针、推演之间显式分级；无法验证的关键合同不能获得相应 PASS。
4. 有风险的系统/原生实验必须经过授权与隔离门禁，不得为了取得审查 PASS 而超范围执行。

### R08 — 缺陷修复与新快照回归

1. 修复后重新绑定快照，验证原缺陷从可证实失败转为可证实修复（优先原 RED→GREEN）、合法路径回归、适用相邻路径和新增独立反例。
2. 对不安全或不可重复的历史 RED，只有本版本明确获得批准、且等效原始失败证据已独立核验时才可替代；不得把开发者口头描述等同于 RED。
3. 历史结果只可在代码/配置/依赖/环境/调用链适用性经独立核验后作为辅助证据，不能自动继承旧 PASS。
4. 所有未运行验证记为 `NOT_RUN` 和原因、风险、放行影响。

### R09 — 进度、证据、缺陷与等级分别报告

每份角色报告至少记录：
- `REVIEW_PROGRESS: REVIEW_IN_PROGRESS | REVIEW_COMPLETE | REVIEW_INCOMPLETE | SNAPSHOT_CHANGED`（完成评估不等于测试全部执行）；
- `EVIDENCE_STATUS: SUFFICIENT | INSUFFICIENT | NOT_ASSESSED`；
- `VERDICT: PASS | FAIL | BLOCKED | CONDITIONAL | NOT_ISSUED`；
- `REVIEW_SCOPE: FIX | TARGETED | FULL`、`REVIEW_LEVEL: FIX_PASS | TARGETED_REVIEW_PASS | ROLE_FULL_SCOPE_PASS | NONE`；
- `INTEGRATION_STATUS: PASS | FAIL | NOT_TESTED`，独立于代码复审；
- 直接证据、运行/未运行验证、P0–P3、未覆盖项与最小关闭条件。

状态举例：
- 已证实违反合同：`REVIEW_COMPLETE + SUFFICIENT + FAIL`；
- 审查完成但关键证明缺失：`REVIEW_COMPLETE + INSUFFICIENT + BLOCKED`；
- 尚未完成评审活动：`REVIEW_INCOMPLETE + NOT_ASSESSED + NOT_ISSUED`；
- 证据足够且无阻断：在明确范围内记录相应 PASS。
不能把 `REVIEW_COMPLETE` 当作 PASS，也不能把 `FIX_PASS/TARGETED_REVIEW_PASS` 当作整体 FULL。

### R10 — 完整代码验收门槛与签收权

`FULL_CODE_REVIEW_PASS` 仅相对于明确 `REVIEW_TARGET / CONTRACT_SCOPE / SNAPSHOT_ID` 成立，且必须同时满足：
1. R01 对受审范围完整性与稳定性的证据资格通过，规则与合同版本固定。
2. B/C 两份独立、同一快照且覆盖完整目标范围的角色级通过；必要的人类或账户独立性要求另外满足。
3. R03–R08 的完整合同矩阵、适用正反/边界/异常、独立反例、真实执行链和相邻高风险影响有充分证据。
4. P0/P1/P2 所有适用阻断项关闭，并经过独立复核；未验证与剩余风险没有阻止完整签收的缺口。
5. 安全、授权和本阶段附加门禁均满足，`R10_STATUS: ELIGIBLE | BLOCKED | INCOMPLETE` 明确列明依据。
6. A 可以核对双审与门禁并报告 `ELIGIBLE`；不能代写 B/C、不能自行把两个角色 PASS 提升为已独立签署的整体结论。

`FULL_CODE_REVIEW_PASS` 不等于 `INTEGRATION_PASS`，两者均不产生自动合并、发布、部署或扩大原生实验的授权。

## 三、评审输出的最低证据要求

- 规则版本、权威合同及范围、审查对象/版本/轮次、前后快照、身份模式。
- 适用合同矩阵：正向/反向/边界/异常、源码位置、独立反例、真实/Mock/静态/未运行验证。
- 原始证据位置、运行环境与实际被测代码身份、退出结果、预期失败和意外失败区分。
- P0–P3 可复现问题与关闭条件，缺证与残余风险。
- 角色级结论、上述三维状态与等级；阶段下一步不得越过授权门禁。

## 四、禁止事项

不得伪造执行/测试；不得用开发者自述、测试计数、历史 PASS、CI GREEN 或另一评审者报告替代独立证据；不得改写旧 Review、降低权威合同、修改受审产品代码或进行未授权高风险操作；任何新规则必须在批准并同步后用于后续轮次。

## 五、启用与权限边界

本规范的独立批准、用户确认及三个 Project 的同版全文读取核验，是实际启用的前提；打包、改名或单个 Project 上传均不构成生效。只对明确采用 V2.0 的审查轮次实施本规范，不改写已有 Review，也不跨快照继承 PASS 或已关闭问题的资格。项目专有且经授权的更严格安全合同仍必须执行。
