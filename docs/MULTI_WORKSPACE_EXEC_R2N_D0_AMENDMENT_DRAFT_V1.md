## 3. Proposed D0 section 0.1 and 0.4 normative text

**Proposed 0.1.A - Profiles and admission.** Three mutually exclusive operator-side security profiles are recognized for a future separately approved product: preview_only (default, present F1 denial), native_limited (trusted host-native limited cleanup), and strict_f3 (OS-enforced bounded-domain complete cleanup, independently unqualified). A remote API request cannot select/change a profile, authorize a backend, supply proof, grant consent or reset an attempt. No backward-compatible extension of schema v1 may implicitly enable native_limited or strict_f3. All unknown profile/config/backends/versions fail closed. The two current server/Workspace Exec opt-ins grant only request eligibility.

**Proposed 0.1.B - Default preserved.** Every installed ordinary non-preview Multi-Workspace Exec still denies exec_cleanup_proof_required before Worker/intent/Runner/process. Valid Preview remains validated and bounded; disabled, quarantined, state-unavailable and proof-required error precedence is preserved. Authorised File Write and Git, including Git's independent subprocess, must remain legally usable under their own grants even when Exec is denied or quarantined. REST and official MCP must continue to use the same WorkspaceService decision; /info and /health are truthful and cannot advertise future capability from config alone.

**Proposed 0.4.A - Limited exception, non-sandbox.** The general D0 full-descendant-cleanup requirement remains binding for strict_f3. A distinct native_limited mode MAY be independently proposed, implemented, qualified and ultimately activated after separate approvals, for code explicitly trusted by the local operator in the changing Workspace and its host Direct/Pipenv/Go execution environment. This mode does not isolate code from Gateway OS-user filesystem/network/credentials or ensure full descendant/process tree cleanup, rollback of effects, or an enforced total process count. Even after leader reap and authenticated original-group absence it must record full_descendant_tree_clean=not_proven. A second mode never inherits any other mode's cleanup proof or silently falls back.

**Proposed 0.4.B - Hard unqualified behavior.** Current F1 remains unconditionally deny-only. Future native_limited positivity MUST NOT be offered without independently reviewed macOS lifetime/identity and at-signal target binding, exact source and backend qualification, safe interprocess state ownership, explicit local consent and a supported serializer that orders revoke versus actual irreversible launch. Existing CommandRunner start_new_session/killpg, a pre-check of PID/PGID, Mock/Fake/T0, return code, heartbeat, EOF and absence of observed detached descendants do NOT qualify. If supported no-collateral-signal target identity or bounded observation cannot be independently demonstrated, send NO SIGNAL, enter UNKNOWN/global quarantine for uncertain live attempts, and keep Native positive NO-GO.

**Proposed 0.4.C - Activation sequencing.** Written risk-contract approval, independently B/C-reviewed operative D0 amendment, independently approved source/config/schema/Runner changes, explicitly authorized native macOS ARM64 disposable T2 tests, full applicable code reviews/integration and separate owner production enablement are distinct approvals. This D0 exception can never be inferred from accepting Candidate A in design, installing a branch, selecting a profile or receiving a design TARGETED_PASS.

## 4. Proposed D0 sections 2.1 and 3 - operator authority and persistence

**2.1.A - Operator consent.** Future local-only, versioned, private consent must bind exactly: profile=native_limited; trust_scope=mutable_workspace; canonical Workspace plus pinned root dev+ino; effective server/Workspace Exec privileges and exec_paths/runner scope fingerprint; installed backend implementation/version/config fingerprint; exact risk-contract version and readable host-user/residual-process/irreversible-effects acknowledgment; revocation state and optional expiry. Only a trusted separately reviewed *local operator* authority may create/revoke/reissue. REST/MCP/CLI/environment, a workspace file, a test flag, an arbitrary untrusted actor or a copied old record NEVER qualifies. The chosen trust scope intentionally permits future in-root legal File/Git/source/Pipenv edits without per-byte SHA approval, NOT a claim those edits are harmless or independently attributed to a human.

**2.1.B - Three separate identities.** consent_epoch is durably fenced and incremented on issue/revoke/reissue and binding changes, not a normal restart or mutable source Git HEAD change. service_owner_generation rotates with each new private owner.lock acquisition/restart. attempt_generation and attempt_id are newly unique and cannot be reused or carried to a new owner. These are different authorities: a persisted consent record may remain valid across a restart while all stale owner/attempt callbacks are rejected. A valid consent does NOT override an armed boot-deny fence or UNKNOWN state.

**3.A - Distinct future schema.** Existing ExecStateStore v1 PREPARED/RUNNING/UNKNOWN/RETIRED records and S2 offline v2 Fake data remain isolated and NONOPERATIVE for Native. A new explicit, separately reviewed Native state/consent schema is needed; the historical v1 group-only RETIRED and test grant can never migrate to RETIRED_LIMITED/RETIRED_PROVEN or mint owner consent. Mixed versions, copied epochs, file identity drift, unsupported downgrade, invalid owner lock and torn state fail closed while retaining evidence. All records are private, bounded, pinned-FD/no-follow, owner-locked and fsynced; never persist raw argv/environment/output/secrets.

**3.B - Armed durable boot-deny fence (B91-R001-P3-02 candidate remedy).** Before authorizing a *first possibly irreversible Native start* for an ownership generation, the reviewed backend must durably precommit an independent, versioned, owner-bound **NATIVE_UNRESOLVED_ON_RESTART** safety fence (and the PREPARED intent) such that an incomplete final write, orphan observer, ENOSPC or crashed owner can NEVER reboot into a false healthy Native state. A minimum conservative policy is:
1. Create and fsync an initialized Native-specific state namespace, boot admission policy and reserved fixed-size fail-closed marker **before** any possible launch; inability to reserve or verify means NO START. A missing/invalid marker within a previously initialized native state namespace is corruption, NEVER auto-create a healthy empty one.
2. Arm and durably fsync the restart-deny marker before PREPARED/STARTING dispatch. A live healthy owner may perform future, independently reviewed limited operations while the armed marker is present only after other consent/attempt/grant checks; the marker NEVER itself authorizes positive Exec.
3. The marker remains armed across RETIRED_LIMITED and service restart because original-group absence does not prove escaped descendants absent. After restart, read the marker and old attempts BEFORE granting any Exec; retain current consent bytes but deny Native admission and require separately approved offline evidence/recovery. A clean restart alone never clears it.
4. A late survivor/quarantine latch that cannot allocate/fsync due to quota exhaustion MUST close new admission synchronously in memory and retain the already durable boot-deny marker as the fail-closed restart witness; no fallback to an older healthy consent snapshot. Never acknowledge durable publication of late evidence that failed to persist. Preserve preexisting evidence and report unavailable/uncertain.
5. Reserve space/journal capacity for a bounded orphan/quarantine event before permitting a new launch, or refuse admission. The exact on-disk atomicity, directory fsync, power-loss persistence and reserved-marker layout remain FUTURE IMPLEMENTATION PROOF OBLIGATIONS, not claimed validated by this text. The old valid v1 store has no such Native marker and cannot bootstrap positive Native merely by being empty.

**3.C - Quotas and forensics.** Preserve finite 4096 attempt records, max 4096 bytes per record and 16 MiB attempt-payload budget, with separately accounted fixed safety markers and any independently justified reservation. Store stable limited-retirement attribution tombstones after response/slot release, without TTL or quota eviction of unresolved or limited-retired linkage to admit new Exec. At capacity, deny new attempts, retain known evidence, and quarantine; do not assume 1-per-Workspace/4-instance managed slots bound OS descendants. If a late event cannot authenticate attribution, preserve an orphan/uncertain quarantine without guessed PID signalling. A hypothetical alternative to the permanently armed restart-deny policy must independently demonstrate equivalent crash/ENOSPC/late-survivor proof before use; no silent safety relaxation is accepted.

## 5. Proposed D0 section 4 - exact launch/revoke sequencing

1. Under a reviewed, exclusive owner-controlled state/admission authority, check global and Workspace Exec permission, validated argv/cwd/runner, durable state health, owner.lock, consent_epoch, pinned root/permissions/backend and global quarantine. If Native backend qualification is missing, deny before Worker/PREPARED. Maintain existing precedence exec_disabled -> exec_quarantined -> exec_state_unavailable -> exec_cleanup_proof_required -> busy (for valid requests).
2. Only a genuinely qualified future positive attempt may hold one Workspace/instance Worker slot and commit+fsync PREPARED and the armed boot-deny fence BEFORE backend allocation or process creation. Record a separate fsynced STARTING and unique attempt owner/binding.
3. Immediately before the **first irreversible backend start**, revalidate latest local durable consent_epoch, owner_generation, attempt token, root dev+ino, effective Exec-scope/backend identity and global late-survivor latch under the same reviewed serialized authority as revoke. PREPARED is NOT grandfathered permission.
4. **Revoke-first:** revoke durably linearizes before first start -> NO START (exact counter 0); fence PREPARED, leave UNKNOWN/global quarantine pending separately reviewed no-start proof. A code path that calls OS spawn after dropping a userspace lock without a proven atomic ownership/dispatch mechanism is NOT qualified to assert this invariant.
5. **Start-first:** a single irreversible start may already have host effects when revoke commits. New admissions/starts stop; reconcile only that same attempt, no duplicate start after ACK loss or client retry. Persist UNKNOWN/quarantine if identity, result, cleanup, fsync or ordering uncertain; never claim to undo side effects.
6. Lease/slot release is after durable limited terminal or UNKNOWN classification; quarantine remains global and any possibly live external resource remains unresolved/accounted for after Worker release. Reboot cannot issue signals from saved numeric PID/PGID.

If the serialized start boundary or supported macOS identity primitive remains unproven, no future code change may expose a positive route; it must preserve F1's deny-only behavior.

## 6. Proposed D0 sections 5 / 7J - limited retirement and late survivor

Future Native only: leader directly reaped, original group independently authenticated absent with race-safe current identity, correct consent/owner/backend, no **positively observed** detached descendant, bounded cleanup and final fsync MAY yield RETIRED_LIMITED with cleanup_scope=original_group_only and full_descendant_tree_clean=not_proven. It is never RETIRED_PROVEN, full_tree_qualified, a Strict domain proof or evidence of arbitrary escaped descendant absence. A known live detached survivor at ANY time, uncertain group, bad final persistence, failed signal ownership or a stale callback forces UNKNOWN/global QUARANTINED.

A positively attributed late survivor may arrive after RETIRED_LIMITED fsync, result commitment, response receipt, Worker release, another attempt's PREPARED, or service restart. Under the same admission/last-start authority, close further Exec admission and durably latch quarantine, supersede A's limited record into UNKNOWN while preserving immutable earlier result ID and evidence, and conservatively handle any already-dispatched B. If late evidence wins while B only PREPARED, B starts zero times; if B's first start won first, B's effects are already possible and must be reconciled independently. Attribution missing after archive => orphan uncertain global latch, not guessed signal or silent ignore. Failure to persist the late event leaves the armed boot-deny fence and live in-memory rejection; NEVER transition to healthy on restart.

## 7. Proposed D0 section 6 - commit/transport order and truthful outcomes

**Three distinct results:** (i) command executed/outcome/timeout/capped bytes, (ii) cleanup scope/evidence and full_descendant_tree_clean=not_proven for all Native, (iii) delivery intent, server-side response decision and actual transport acknowledgement only when proven. HTTP/MCP waiter cancellation and network loss never free a possibly live attempt or justify retry.

**B91-R001-P3-01 precise proposed decision point:** define a small owner-controlled **server response-decision linearization** serialized with the same global late-survivor quarantine latch and the last pre-start gate. Under this authority, after authenticated limited retirement and final durable state, a response decision either:
- observes that no quarantine has yet durably latched and writes/fsyncs one immutable **LIMITED_HISTORICAL_COMPLETION_COMMITTED** outcome ID, attempt/generation and monotonically ordered decision sequence before releasing the gate; OR
- observes the prior latched event and writes/fsyncs a non-clean **QUARANTINED_OR_CLEANUP_UNKNOWN** decision, with command result only as explicitly partial/historical evidence.

A successful server-side decision is **not** a network write, enqueue, socket ACK or proof of client receipt. After a prior committed limited result, a late event may supersede the current global capability; delayed transport may deliver only that immutable **historical/as-of-decision** result, never a fresh claim that the Workspace is currently healthy or full descendants absent. If no durable response decision has committed when the survivor event wins, the server MUST NOT mint/send a new clean-limited decision. Under a response cancellation before decision commit, no clean result is promised. A blocked/failed decision fsync cannot issue apparently clean success. The actual enqueue/write/ACK and whether an already committed message can be suppressed safely must be specified and tested separately by the future transport code; no atomic socket write is falsely claimed.

**Required prospective adversarial schedule:** A RETIRED_LIMITED fsync -> B late-survivor event -> quarantine latch fsync -> pending server response decision -> must be NOT CLEAN. Opposite ordering A durable limited response-decision first -> late survivor -> delivery delayed -> may show bounded immutable historical result, with current public status quarantined and no retroactive rewriting. Include waiter cancellation, fail-durable-decision, no verified transport ACK, concurrent B PREPARED/start-first, and independent SDK/REST serializers. If the future code cannot provide a concrete serialized decision/late-latch implementation, Native positive stays NO-GO.

Current F1 /info /health remains available=false and completion_capability=none. A future source-reviewed, qualified limited backend may advertise native_original_group_limited ONLY after separate user/operator activation and correct current evidence, NEVER full_tree_qualified or Strict. Current result/status must distinguish a past limited command outcome from present eligibility.
